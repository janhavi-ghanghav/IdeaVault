# Decision Log

Architectural decisions made during development of IdeaVault, with context and tradeoffs.

---

## 1. BullMQ over synchronous AI calls

**What:** Idea enrichment runs asynchronously via BullMQ job queue, not inline in the API handler.

**Context:** Initial implementation called the Groq API synchronously inside `POST /ideas`. Response time: ~2200ms. Under concurrent load this exhausted the Postgres connection pool.

**Decision:** Enqueue a BullMQ job on idea creation. API returns in ~80ms. A separate Node worker process picks up jobs and calls the Python AI service independently.

**Tradeoffs:**
- Pro: Fast API response, resilient to AI service slowness, automatic retry on failure
- Con: Enrichment is eventually consistent — the UI shows "Enriching..." briefly

**At 10x scale:** Add dead letter queue monitoring, autoscale worker pods based on queue depth, consider dedicated job processing infrastructure.

---

## 2. Redis pub/sub as worker-to-Socket.io bridge

**What:** Node worker publishes enrichment completion to a Redis channel. API server subscribes and emits via Socket.io to the correct user room.

**Context:** Worker and API server are separate Node processes. They cannot share memory or EventEmitter. The browser needs to know when enrichment finishes without polling.

**Decision:** Worker publishes to `enrichment:complete` channel. API server (which owns the Socket.io server) subscribes and forwards to the user's room.

**Implementation detail:** Two separate IORedis connections are required — a Redis connection in subscribe mode cannot execute other commands.

**Tradeoffs:**
- Pro: Worker and API server are fully decoupled
- Con: Redis pub/sub doesn't scale across multiple API instances without Redis Cluster

**At 10x scale:** Move to Redis Cluster or replace pub/sub with Kafka for horizontal scalability.

---

## 3. Separate Enrichment table from Idea table

**What:** Enrichment data lives in its own table with a 1-to-1 relation to Idea, not as columns on the Idea table.

**Context:** Enrichment is computed data generated by AI. Idea is user data entered directly.

**Decision:** Separate tables. Dashboard list queries don't join Enrichment unless needed. Enrichment can be regenerated (re-run AI, update enrichment row) without touching the Idea row.

**Tradeoffs:**
- Pro: Clean separation of user data vs computed data, cheaper list queries
- Con: Requires a join when you need enrichment alongside idea data

---

## 4. pgvector over dedicated vector database

**What:** Embeddings stored as `vector(384)` column in Postgres using the pgvector extension.

**Context:** Each idea gets a 384-dimensional embedding for semantic similarity. Options were: pgvector, Pinecone, Weaviate, Qdrant.

**Decision:** pgvector. At thousands of ideas, cosine similarity queries complete in under 20ms. Operationally simpler — one less service, one less connection, migrations in the same schema.

**Tradeoffs:**
- Pro: No additional service, same schema, fast enough at current scale
- Con: No HNSW index currently (using exact search), will slow at 500k+ vectors

**At 10x scale:** Add HNSW index (`CREATE INDEX ON "Idea" USING hnsw (embedding vector_cosine_ops)`). At 500k+ vectors, migrate to Qdrant or Pinecone.

---

## 5. fastembed for local embeddings

**What:** BAAI/bge-small-en-v1.5 model runs locally via fastembed, not via OpenAI Embeddings API.

**Context:** Need to embed idea text as 384-dim vectors. Options: OpenAI ada-002 (1536-dim, $0.0001/1K tokens), fastembed local (384-dim, free).

**Decision:** fastembed. Zero cost, no external API dependency, ~50MB model, loads once at startup and is reused for every request.

**Tradeoffs:**
- Pro: Free, fast, no external dependency, works offline
- Con: Lower quality than OpenAI's models, CPU-only inference

---

## 6. SM-2 as a pure function

**What:** Spaced repetition algorithm implemented as `calculateNextReview(SM2Input): SM2Output` with no side effects.

**Context:** SM-2 algorithm needs to compute next review interval given current state. Could have been implemented as a method that reads/writes DB directly.

**Decision:** Pure function. Input is the current SM-2 state. Output is the next state. The route handler reads state from DB, calls the function, writes result back to DB.

**Tradeoffs:**
- Pro: Trivially unit testable (7 tests, zero mocks), easy to reason about
- Con: Slightly more code in the route handler

---

## 7. Token bucket rate limiting over fixed window

**What:** Redis INCR + EXPIRE for rate limiting idea enrichment to 10 per hour per user.

**Context:** Need to prevent abuse of the Groq API. Fixed window rate limiting has a boundary vulnerability: a user can make 10 requests at 11:59pm and 10 at 12:00am — 20 requests in 2 minutes.

**Decision:** Token bucket via Redis INCR + EXPIRE. First request sets a 1-hour expiry. Counter increments on each request. Works across multiple API instances since state is in Redis.

**Tradeoffs:**
- Pro: No boundary vulnerability, horizontally scalable
- Con: Simple implementation — a true sliding window would be even more accurate

---

## 8. Per-route preHandler for authentication

**What:** Clerk JWT verification applied as `preHandler` on each protected route individually.

**Context:** Fastify uses plugin encapsulation — hooks registered in a parent plugin scope do not automatically apply to routes registered in sibling plugin scopes via `register()`. A global `addHook('preHandler', authenticate)` silently failed during development.

**Decision:** Explicit `{ preHandler: authenticate }` on every protected route. Verbose but predictable and impossible to accidentally leave a route unprotected.

**Tradeoffs:**
- Pro: Explicit, no silent failures, easy to audit which routes are protected
- Con: More repetitive code

---

## 9. OpenTelemetry distributed tracing

**What:** W3C traceparent header propagated from Node worker to Python AI service. Both export spans to Jaeger.

**Context:** Enrichment pipeline spans two services (Node worker → Python FastAPI). When something breaks or is slow, logs across two services are hard to correlate by timestamp alone.

**Decision:** Node worker injects traceparent into HTTP headers before calling Python. Python is configured with CompositePropagator accepting W3C TraceContext and B3 formats. Both export to Jaeger via OTLP HTTP. One request = one connected trace in Jaeger.

**Tradeoffs:**
- Pro: Single timeline across both services, easy to identify bottlenecks
- Con: OTel adds startup overhead, fs instrumentation disabled (too noisy)
